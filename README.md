## English

### Images and tags

Both images target x64. The Linux image uses **Ubuntu 24.04**; the Windows image uses
**Windows Server Core LTSC 2022** and requires a compatible Windows container host.
A Linux Docker engine cannot run the Windows image.

| Platform | Version tag (example) | Moving tag |
| --- | --- | --- |
| Ubuntu 24.04 | `1.0.0-ubuntu24.04` | `latest-ubuntu24.04` |
| Windows LTSC 2022 | `1.0.0-windows` | `latest-windows` |

Images are published to `<dockerhub-user>/github-actions-runner` and
`<registry>.azurecr.io/github-actions-runner`. Use versioned tags for reproducibility.
The container release version is independent of the bundled `actions/runner` version.

### Start a runner

Generate a **runner registration token**, not a personal access token, in the target
organization or repository under **Settings > Actions > Runners > New self-hosted runner**.
Registration tokens expire after one hour. Supply credentials at runtime only.

| Environment variable | Required | Meaning |
| --- | --- | --- |
| `RUNNER_URL` | Yes | Organization or repository URL; no default |
| `RUNNER_TOKEN` | Yes | Registration token for that exact URL |
| `RUNNER_NAME` | Yes | Runner name and additional `runs-on` label |

Linux example, after setting these three variables in your shell:

```bash
docker run -d --name gha-linux \
	-e RUNNER_URL -e RUNNER_TOKEN -e RUNNER_NAME \
	<dockerhub-user>/github-actions-runner:latest-ubuntu24.04
```

Windows example, after setting the variables in your PowerShell environment:

```powershell
docker run -d --name gha-windows `
	-e RUNNER_URL -e RUNNER_TOKEN -e RUNNER_NAME `
	<dockerhub-user>/github-actions-runner:latest-windows
```

For private-registry images, authenticate with `docker login <registry>.azurecr.io`
and replace the image prefix. Select your runner by name-label and operating system:

```yaml
jobs:
	example:
		runs-on: [self-hosted, Linux, X64, my-linux-runner]
		steps:
			- run: echo "Running on my Linux runner"
```

For Windows use `[self-hosted, Windows, X64, my-windows-runner]`.
Organization runner-group access rules still determine which repositories may use a runner.

### Repository setup

Configure these repository Actions secrets before publishing:

| Secret | Purpose |
| --- | --- |
| `USER_DOCKERHUB` | Docker Hub username and image namespace |
| `PAT_DOCKERHUB` | Docker Hub access token with push permission |
| `URL_AZURECONTAINERREG` | Registry hostname, e.g. `example.azurecr.io`, or its HTTPS origin; no repository path |
| `USER_AZURECONTAINERREG` | Registry login username |
| `PW_AZURECONTAINERREG` | Registry password or token with push permission |

Both registries must be reachable from GitHub-hosted runners. A registry behind a
private endpoint requires a network-connected self-hosted build runner instead.
Docker Hub must allow the supplied user to push to `github-actions-runner`.

Enable **Settings > Actions > General > Allow GitHub Actions to create and approve
pull requests**. Set **Settings > Pages > Build and deployment > Source** to **GitHub Actions**.
Ensure `luth2` can be assigned to repository PRs.

### Releases and automation

- `release.yml`: validates the project, runs semantic-release on `main`, then builds
	Ubuntu and Windows images in a matrix and pushes each image to both registries.
	Pull requests build and smoke-test both images without registry credentials or pushes.
- Conventional Commits: `fix:` creates a patch, `feat:` a minor, and a
	`BREAKING CHANGE:` footer a major release. The first release is `1.0.0`.
	Use a release-worthy first commit such as `feat: add runner release pipeline`.
	Squash-merge PRs with a matching Conventional Commit title.
- Documentation-only and ordinary `chore:` commits do not publish images.
	Release notes and Git tags are generated by semantic-release; nothing is published to npm.
- `update-runner.yml`: checks official stable `actions/runner` releases daily at
	06:23 UTC and updates both versions and SHA256 digests in a `fix(deps)` PR assigned to `luth2`.
	Both assets must be present; Docker builds verify their SHA256 checksums.
- Dependabot checks workflow Actions and release/documentation npm tooling weekly;
	all its PRs and all other newly opened/reopened PRs are assigned to `luth2`.
- `pages.yml`: publishes this README as English/German documentation.

Runner-update PRs use `GITHUB_TOKEN`, which does not trigger normal PR CI workflows.
Manually run **Validate, release and publish containers** on the update branch to
validate it before merging. Non-`main` manual runs build without publishing.
Main-branch releases and image publication share one workflow, so no release-event PAT is needed.

If image publishing fails after a release was created, rerun the workflow: it reuses
the existing version at that commit. Older releases cannot overwrite `latest` through a rerun.
Registry pushes are not transactional; a failed run can leave one registry or platform updated.

### Operations and local checks

```bash
docker build -f Dockerfile.linux -t github-actions-runner:local .
npm ci --ignore-scripts
npm test
npm run docs:build
```

Build Windows with `docker build -f Dockerfile.windows -t github-actions-runner:local .`
on a Windows container host. The generated Pages site is in `docs/_site/`.

The runner name must be unique. `--replace` replaces an existing registration of the
same name; do not run two containers with that name. Registration is skipped when
the container already has `.runner`; changed URL/name values require recreating it.
The token is unset before the runner starts, but Docker administrators can still
inspect the container's configured environment. Do not bake credentials into images.

These are persistent runners: shutdown does **not** automatically deregister them.
Delete stale registrations in GitHub when replacing/removing containers. Jobs share
the runner workspace until the container is recreated; only run trusted workflows.
No Docker socket or extra build toolchains are included. The Linux image includes Git;
install additional tools, including Git on Windows, as your jobs require.
Runner self-updates remain enabled; rebuild and redeploy for fresh base-image patches.

Both Dockerfiles declare `owner=luth2` and the OCI author `luth2 (https://github.com/luth2)`.
The npm release-tool dependency tree currently has upstream security advisories that
compatible updates do not resolve. Install scripts are disabled, PR jobs have no registry
credentials, and publishing runs only on trusted `main`; review `npm audit` before deployment.

## Deutsch

### Images und Start

Beide Images sind fuer x64: **Ubuntu 24.04** beziehungsweise **Windows Server Core
LTSC 2022**. Windows benoetigt einen kompatiblen Windows-Containerhost, keine Linux-Engine.
Veroeffentlicht wird nach Docker Hub und in die private Registry, jeweils unter
`github-actions-runner`. Tags sind beispielsweise `1.0.0-ubuntu24.04` und
`1.0.0-windows`; bewegliche Tags heissen `latest-ubuntu24.04` und `latest-windows`.
Image-Version und enthaltene GitHub-Runner-Version sind voneinander unabhaengig.

Beim Start muessen `RUNNER_URL`, `RUNNER_TOKEN` und `RUNNER_NAME` gesetzt sein.
Die URL bezeichnet die Zielorganisation oder das Zielrepository und hat keinen Standardwert.
Der Token ist ein dazu passender **Registrierungstoken**, kein PAT; er laeuft nach einer Stunde ab.
Den Token erzeugst du unter **Settings > Actions > Runners > New self-hosted runner**.
Nutze die Linux-/PowerShell-Startbefehle im englischen Abschnitt mit deinen Umgebungsvariablen.

Der Name wird auch als Label hinterlegt:

```yaml
runs-on: [self-hosted, Linux, X64, mein-linux-runner]
```

Unter Windows verwende `[self-hosted, Windows, X64, mein-windows-runner]`.
Bei Organisations-Runnern gelten zusaetzlich die Zugriffsregeln der Runner-Gruppe.

### Einrichtung und Versionierung

Die fuenf oben beschriebenen Secrets sind erforderlich: `USER_DOCKERHUB`,
`PAT_DOCKERHUB`, `URL_AZURECONTAINERREG`, `USER_AZURECONTAINERREG` und
`PW_AZURECONTAINERREG`. Die Registry-URL muss ein Hostname oder eine HTTPS-Adresse
ohne Repository-Pfad sein. Beide Registries muessen von GitHub-hosted Runnern
erreichbar sein; fuer einen privaten Netzwerk-Endpunkt brauchst du eigene Build-Runner.

Erlaube GitHub Actions unter **Settings > Actions > General** das Erstellen von PRs.
Waehle unter **Settings > Pages > Build and deployment > Source** die Option
**GitHub Actions**. `luth2` muss im Repository als Assignee verfuegbar sein.

Auf `main` erzeugt semantic-release anhand von Conventional Commits die Version:
`fix:` = Patch, `feat:` = Minor, `BREAKING CHANGE:` = Major; erste Version = `1.0.0`.
Der erste Commit sollte beispielsweise `feat: add runner release pipeline` heissen.
Beim Squash-Merge muss der PR-Titel diesem Format entsprechen. Reine Doku- oder
normale `chore:`-Commits loesen keine Image-Veroeffentlichung aus.

Nach dem Release baut die Matrix Ubuntu und Windows auf passenden Hosts, prueft die
Runner-Binaerdatei und pusht Versionstags und bewegliche Tags in beide Registries.
PRs bauen und testen ohne Registry-Secrets und ohne Push. npm wird nicht veroeffentlicht.

### Automatische Pflege und Betrieb

Der Runner-Update-Workflow prueft taeglich um 06:23 UTC offizielle stabile Releases
aus `actions/runner`. Beide Downloads und SHA256-Pruefsummen muessen vorliegen.
Ein `fix(deps)`-PR aktualisiert beide Dockerfiles und wird `luth2` zugewiesen.
Dependabot aktualisiert Actions und npm-Werkzeuge woechentlich. Auch alle anderen
neu erstellten oder wieder geoeffneten PRs werden `luth2` zugewiesen.

Da Update-PRs mit `GITHUB_TOKEN` keine normale PR-CI ausloesen, starte vor dem Merge
**Validate, release and publish containers** manuell auf dem Update-Branch.
Manuelle Runs ausserhalb von `main` bauen ohne Veroeffentlichung.
Bei einem fehlgeschlagenen Registry-Push kann der Run dieselbe Release-Version
wiederverwenden. Alte Releases duerfen `latest` nicht zuruecksetzen; Registry-Pushes
sind trotzdem nicht atomar und koennen teilweise erfolgreich sein.

Runner-Namen muessen eindeutig sein: `--replace` ersetzt die gleichnamige Registrierung.
Vorhandene Container behalten ihre Registrierung; fuer eine neue URL oder einen neuen
Namen erstelle den Container neu. Der Token wird vor dem Runner-Start entfernt,
bleibt aber fuer Docker-Administratoren in der Container-Konfiguration einsehbar.
Keine Secrets ins Image schreiben.

Beim Stoppen erfolgt keine automatische Abmeldung. Entferne veraltete Runner in
GitHub. Persistente Runner teilen ihren Arbeitsbereich zwischen Jobs: nur
vertrauenswuerdige Workflows ausfuehren. Docker-Socket und weitere Toolchains sind
nicht enthalten; unter Windows auch Git bei Bedarf installieren. Runner-Selbstupdates
bleiben aktiv. Fuer aktuelle Basisimage-Patches Images neu bauen und Container ersetzen.

Lokale Pruefung: `npm ci --ignore-scripts`, `npm test`, `npm run docs:build`.
Die generierte zweisprachige Seite liegt unter `docs/_site/`.

Beide Images tragen `owner=luth2` sowie das OCI-Autorenlabel mit dem GitHub-Profil.
Die npm-Releasewerkzeuge enthalten derzeit nicht kompatibel behebbare
Upstream-Sicherheitsmeldungen. Installationsskripte sind deaktiviert; PR-Jobs erhalten
keine Registry-Zugangsdaten. Pruefe `npm audit` vor der Inbetriebnahme.
